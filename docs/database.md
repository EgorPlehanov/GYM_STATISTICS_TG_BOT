# База данных

## Назначение слоя

Слой базы данных находится в `app/db` и отвечает за:

- SQLAlchemy metadata;
- модели;
- подключение к PostgreSQL;
- фабрики sync/async-сессий;
- миграции Alembic;
- загрузку справочных данных;
- repositories для запросов.

## Структура

```text
app/db/
  base.py
  session.py
  models.py
  seed.py
  seed_data/
  repositories/

migrations/
  env.py
  script.py.mako
  versions/
```

## Пользовательская модель

Пользователь имеет внутренний primary key:

```text
user.id
```

Telegram id хранится отдельно:

```text
user.telegram_id
```

Это нужно, чтобы в будущем можно было добавить другие способы авторизации без привязки всей базы к Telegram id.

## Роли и доступ

RBAC хранится в двух таблицах:

```text
role
user_role
```

`role` содержит справочник ролей приложения. На старте загружаются базовые роли:

- `owner`;
- `admin`;
- `user`.

Runtime-код не создает и не обновляет справочник ролей. Если нужной роли нет,
это считается ошибкой инициализации базы: нужно проверить миграции и загрузку
seed-данных.

`user_role` связывает пользователя с ролью и хранит, кто назначил роль, если это
известно. У одного пользователя не может быть две одинаковые роли.

Роли работают как additive roles: несколько ролей пользователя складываются.
Например, владелец системы имеет обычную пользовательскую роль `user` и
административную роль `owner`.

При создании обычного пользователя ему назначается роль `user`. Если Telegram id
совпадает с `MAIN_ADMIN_ID`, пользователь дополнительно получает роль `owner`.
Это bootstrap-механизм для первичного доступа к админским функциям.

## Дата тренировки

`training.date` хранится как SQL `DATE`, потому что это календарный день тренировки, а не
точное время события.

Разделение дат в модели:

- `training.date` - день тренировки;
- `set.execution_time` - время выполнения конкретного подхода;
- `created_at` и `updated_at` - технические даты создания и обновления записей.

В dev-режиме проект пока может пересоздавать БД полностью, поэтому это решение
зафиксировано в начальной Alembic-схеме без отдельной миграции преобразования
`DateTime -> Date`.

## Миграции

Структура базы управляется через Alembic.

Применение миграций:

```text
uv run alembic upgrade head
```

Создание новой миграции:

```text
uv run alembic revision --autogenerate -m "описание изменения"
```

## Справочники

Seed-данные находятся в:

```text
app/db/seed_data/
```

Загрузка справочников:

```text
uv run python -m app.db.seed
```

Seed-команда добавляет только отсутствующие записи. Проверка существования выполняется по значениям полей, кроме `id`.

## Инициализация и сброс

Обычные сервисы приложения не должны применять миграции или пересоздавать базу при старте.

Для первого запуска или релиза используется явная команда:

```text
docker compose --profile tools run --build --rm migrate
```

Команда `migrate` применяет Alembic-миграции и загружает seed-данные. Флаг
`--build` важен после изменений схемы или справочников: без него Docker Compose
может запустить ранее собранный образ `migrate` со старыми файлами.

Для разработки есть отдельный полный сброс:

```text
docker compose --profile tools run --rm db-reset
```

`db-reset` удаляет схему `public`, применяет миграции и загружает справочники. Команда защищена проверкой `APP_ENV=dev` и не должна использоваться в production.

Полное пересоздание локальной Docker-среды:

```text
docker compose down -v --remove-orphans --rmi local
docker compose pull db
docker compose --profile tools build --no-cache
docker compose up -d db
docker compose --profile tools run --rm migrate
docker compose up -d api bot
```

Профиль `tools` нужен, чтобы в сборку попали `migrate` и `db-reset`.
PostgreSQL-сервис `db` не собирается, а скачивается через `docker compose pull db`.

Бизнес-слой и UI-слои не должны вызывать repositories напрямую. Для сценариев приложения используется `app.domain`.
