# План исправления Telegram-сообщений

## Цель

Сделать надежной работу с двумя видами контролируемых сообщений Telegram:

- результат тренировки в redirect-группе;
- главное интерфейсное сообщение личного сценария тренировки.

Контролируемое сообщение имеет сохраненный `message_id`, который бот в нормальном случае редактирует. Пользователь может удалить такое сообщение, а Telegram не присылает обычному боту отдельный update об удалении. Отсутствие сообщения обнаруживается только при следующем `editMessage*` или `deleteMessage`.

## Ограничение Telegram API

Типы aiogram классифицируют HTTP-ответ, а не конкретную причину, связанную с сообщением:

- `TelegramBadRequest` соответствует HTTP 400 и объединяет отсутствие сообщения, невалидную разметку, неверную клавиатуру и другие ошибки запроса;
- `TelegramNotFound` соответствует HTTP 404 и не указывает, какой именно ресурс не найден;
- `TelegramForbiddenError` означает, что бот не может работать с чатом.

Следовательно, тип исключения сам по себе не позволяет отличить удаленное целевое сообщение от иной ошибки HTTP 400. Разбор `error.message` допустим только внутри одного Telegram-адаптера, который преобразует низкоуровневую ошибку в ограниченный набор доменных результатов. Бизнес-обработчики, renderer и API client не должны сравнивать текст Telegram-ошибок.

## Общие правила

1. Новый `message_id` сохраняется только после успешного `send_message`.
2. Неизвестный `TelegramBadRequest`, сетевая ошибка, rate limit и ошибка Telegram 5xx не являются признаком удаленного сообщения. Они логируются и пробрасываются.
3. `TelegramNotFound` при операции над известным сообщением рассматривается как недоступность целевого ресурса. Попытка отправить новое сообщение допускается только если отправка в этот чат возможна.
4. `TelegramForbiddenError` при отправке в redirect-группу помечает группу недоступной для бота.
5. Для личного сценария тренировки пользовательское действие не применяется, если до его выполнения обнаружено отсутствие основного интерфейсного сообщения.
6. Если backend-изменение уже успешно выполнено, интерфейс отражает фактический результат; backend не откатывается из-за ошибки Telegram.

## Этап 1. Контракт результата сохранения тренировки

### Проблема

`BotTrainingSaveResult` содержит два независимых флага: `created` и `updated`. При создании новой тренировки с подходами оба флага могут быть `True`, потому что создание подходов устанавливает признак обновления. В `redirect_result` сначала проверяется `is_update`, поэтому ветка `is_created` для новой тренировки фактически не используется по назначению.

### Требуемый результат

Ввести единый семантический результат сохранения:

```text
CREATED   - создана новая тренировка;
UPDATED   - изменена существующая тренировка;
UNCHANGED - сохранение не изменило тренировку.
```

`CREATED` имеет приоритет над техническим признаком изменения подходов.

`send_training_result_to_redirect_groups` должен принимать обязательные `training_id` и единый typed-результат, а не параметры `is_update=False`, `is_created=False` и `training_id: int | None`.

Поведение:

- `CREATED`: отправить новый результат в каждую redirect-группу;
- `UPDATED`: обновить существующий результат или восстановить его при отсутствии;
- `UNCHANGED`: не выполнять Telegram/API-вызовы для редиректа.

## Этап 2. Одна операция сохранения связи результата

### Проблема

После повторной отправки сообщения код сначала вызывает `PATCH update`, затем при `updated=False` вызывает `POST create`. Это два сетевых обращения и гонка между ними. В таблице `group_training_result_message` сейчас нет уникального ограничения на `(group_id, training_id)`.

### Требуемый результат

Связь результата определяется парой:

```text
group_id + training_id -> message_id
```

В модели и базовой схеме требуется уникальное ограничение на `(group_id, training_id)`.

В repository реализовать один PostgreSQL upsert:

```sql
INSERT INTO group_training_result_message (group_id, training_id, message_id)
VALUES (:group_id, :training_id, :message_id)
ON CONFLICT (group_id, training_id)
DO UPDATE SET
    message_id = EXCLUDED.message_id,
    updated_at = now();
```

В internal API и `BotApiClient` заменить раздельные методы `create_training_result_message` и `update_training_result_message` одним методом `upsert_training_result_message`.

После успешной отправки сообщения в группу бот выполняет ровно один internal API-вызов для сохранения связи.

### Развертывание схемы

Новая Alembic-миграция не создается. Проект используется в dev-среде, поэтому перед проверкой схемы база и volume пересоздаются полностью. Базовая миграция `0001_initial_schema.py` и SQLAlchemy-модель изменяются синхронно.

Перед пересозданием базы необходимо убедиться, что она не содержит данных, которые требуется сохранить.

## Этап 3. Рефакторинг redirect-результатов

`send_training_result_to_redirect_groups` должен иметь явные ветки:

```text
CREATED:
    send_message
    upsert message_id

UPDATED, message_id отсутствует:
    send_message
    upsert message_id

UPDATED, сообщение успешно отредактировано:
    завершить обработку группы

UPDATED, текст не изменился:
    завершить обработку группы

UPDATED, целевое сообщение недоступно:
    send_message
    upsert message_id

Бот не может писать в группу:
    пометить группу is_bot_banned=True
    продолжить со следующей группой

Неизвестная ошибка:
    записать в лог и пробросить
```

Если сохраненный `message_id` отсутствует, нельзя вызывать `edit_message_text(message_id=None)`. Новое сообщение отправляется сразу.

Необходимо убрать текущую проверку `"same as a current content"`: она не соответствует используемому ответу Telegram `message is not modified` и может создавать дубликаты.

## Этап 4. Telegram-адаптер ошибок сообщений

Выделить единый внутренний адаптер для операций `edit_message_text`, `edit_message_reply_markup` и `delete_message` над контролируемыми сообщениями.

Адаптер возвращает ограниченный typed-результат, например:

```text
APPLIED
NOT_MODIFIED
MESSAGE_UNAVAILABLE
```

Он является единственным местом, где допускается:

- ловить `TelegramBadRequest` и `TelegramNotFound`;
- распознавать подтвержденные варианты отсутствующего сообщения;
- распознавать `message is not modified`.

Неизвестный `TelegramBadRequest` не должен превращаться в отправку дубликата.

Сначала адаптер используется в `redirect_result`, затем применяется в UI-сервисе тренировки. Общий модуль не должен содержать бизнес-правила redirect или FSM.

## Этап 5. Исправление восстановления UI тренировки

Текущий сервис тренировки уже содержит отдельный renderer и `message_id` в typed `TrainingDraft`, но восстановление после `/training` не прошло ручную проверку.

После внедрения адаптера требуется:

1. Перевести `transition_training_screen`, `show_or_recover_target`, `replace_after_backend`, `replace_training_markup` и `delete_training_message` на adapter.
2. Проверить обработку `TelegramNotFound`.
3. При `/training` с активным draft гарантированно создать новый `resume_prompt` или экран результата и сохранить новый `message_id`; после успешной отправки удалить прежнее серверное сообщение. Это покрывает локальное удаление сообщения пользователем, которое Telegram Bot API не сообщает боту.
4. При текстовом вводе и отсутствии UI восстановить предыдущий экран без применения ввода.
5. Для уже завершенной backend-операции при потере UI отправить новый экран фактического результата.
6. Не очищать существующий draft из-за ошибки Telegram, кроме неуспешной отправки самого первого экрана новой тренировки, когда `message_id` еще не получен.

## Этап 6. Логирование и тесты

Добавить структурированное логирование в глобальный error-handler и в Telegram-адаптер. Лог должен содержать:

- класс исключения;
- Telegram-метод;
- `error.message`;
- chat id;
- message id;
- текущий FSM state, если применимо.

Добавить тесты:

- преобразование `TelegramBadRequest` с известными причинами в typed-результаты;
- `TelegramNotFound` при операции над сообщением;
- неизвестный `TelegramBadRequest`, который не создает дубликат;
- `TelegramForbiddenError` при redirect-отправке;
- `CREATED`, `UPDATED`, `UNCHANGED` для redirect;
- upsert связи результата при первом сообщении и повторной отправке;
- `/training` после удаления интерфейсного сообщения;
- текстовый ввод при удаленном UI без изменения draft;
- backend-действие, успешно завершившееся до потери интерфейса.

Проверки после каждого этапа:

```powershell
uv run ruff check app tests
uv run pytest
```

После изменения базовой схемы для dev-среды:

```powershell
docker compose down -v --remove-orphans
docker compose --profile tools run --build --rm migrate
docker compose up -d --build api bot
```

Команда удаления volume необратимо удаляет локальные данные PostgreSQL и применяется только после подтверждения, что эти данные не нужны.
